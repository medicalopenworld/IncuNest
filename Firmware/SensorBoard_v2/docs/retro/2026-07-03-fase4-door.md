## Qué se hizo

Componente `door_sensor`: hall DRV5032FB en IO47, ISR ANYEDGE de solo hand-off (IRAM), `door_task` con debounce y re-aserción periódica, fsm+builder puros con 7 TEST_CASE.

## Aprendizajes

1. **`xTaskNotifyStateClear` ≠ vaciar el contador.** Solo limpia el flag `ucNotifyState`; `ulNotifiedValue` (lo que consume `ulTaskNotifyTake`) queda intacto — el "colapso de ráfagas" no colapsaba nada y dejaba ciclos fantasma de 250 ms. La API correcta es `ulTaskNotifyValueClear(NULL, ~0)`. El reviewer lo verificó leyendo `tasks.c` del kernel: ante APIs de FreeRTOS con nombres parecidos, ir a la fuente.
2. **Edge-only es lossy por naturaleza: toda señal de seguridad necesita re-aserción idempotente.** Un solo evento perdido (cola TX llena) desincronizaba a la motherboard indefinidamente. Patrón fijado: estado periódico + evento por cambio, no solo evento.
3. **Una línea digital con pull-up no distingue "abierto" de "sensor desconectado".** Límite físico, no de firmware: el contrato con la motherboard (README) exige tratar `door_open` sostenido implausible como posible fallo. Las Fases 3/5 deben preguntarse lo mismo: ¿qué lee este sensor cuando está roto?
4. **Las ISR compartidas (`gpio_install_isr_service`) son un singleton con efectos entre fases**: el primero fija los flags para todos; armar la interrupción antes de registrar el handler pierde flancos si otra fase instaló el servicio antes. Configurar con `GPIO_INTR_DISABLE` y armar tras `handler_add`.
